# 首次接入命名空间合并

## 简要计划

1. 在命名空间切换中区分“远端完整替换本机”和“首次接入并合并本地会话”。
2. 为首次接入生成保守的双端语义合并预览；相同 UUID 的不同内容必须由用户选择。
3. 将确认的结果只写入本机并建立目标命名空间 Tracking，不提交远端 Revision。
4. 将恢复备份改为用户明确选择的风险选项；未选择时不保留操作完成后的恢复备份。
5. 为合并规划、冲突、只读远端保证及可选备份行为添加测试，并运行 Rust 与前端验证。

## 详细实施计划

### 当前行为

`switch_namespace` 在目标命名空间不是当前活动空间时下载远端 Head，调用受保护的 exact checkout 完整替换本地会话，并把 Tracking 和活动命名空间更新到该 Head。该路径必定创建数据库、rollout 与项目状态的恢复备份。普通 Pull 只适用于已有活动命名空间和共同 Tracking 基础。

现有 `merge_thread_sets` 是三方合并：需要 base、本地和远端三组线程；它不适合尚未接入过目标命名空间的 B 电脑。

### 目标行为与边界

新增“首次接入并合并本地会话”动作，仅在目标命名空间尚未活动时可用。其远端操作只包含协议/Head/对象读取；不创建或推进远端 Revision。

该动作采用保守的双端接入规则：只存在于一侧的线程保留；同 UUID 且语义 hash 相同的线程去重；同 UUID 且不同的线程生成必须显式选择本地或远端的冲突。缺失不表示删除。确认冲突选择后，将合并线程集物化为本地 Snapshot 并执行一次 checkout，Tracking 指向读取到的远端 Head，活动绑定指向目标命名空间。用户之后必须单独点击 Push 才会发布本地合并结果。

Codex 仍必须完全关闭；本地扫描警告、对象校验、每 Home 写租约、Tracking CAS、不可变对象校验和 Journal 保留。用户要求允许数据丢失，因此 checkout 的“保留完成后可恢复备份”改为显式 `retain_recovery_backup` 选项：未选时仍允许短暂操作内回滚所需的 staging，但在成功完成后清理恢复副本；失败路径尽可能恢复，不能恢复时保留 Journal 并明确报告。这个选项不影响远端数据。

### 实施阶段

1. **核心合并规划**：在桌面同步层添加首次接入准备结构和纯函数，载入并规范化本机、远端线程，按 UUID/hash 生成合并集合与冲突报告。复用既有 `ThreadConflict`、hash 与显式 resolution 校验，避免 SQLite 二进制合并。
2. **确认后本地应用**：增加“解决首次接入冲突并应用”入口。执行前重新扫描本机、重新读取远端 Head，并校验预览指纹，拒绝过期选择。将结果保存为本地 Snapshot，执行带 Tracking 的 checkout；远端只读。
3. **可选恢复备份**：为 checkout API 和 Journal 增加保留标记。默认兼容路径继续保留；首次接入和命名空间替换从 IPC 传入用户选择。成功且未选择保留时清理恢复目录，不把它作为可恢复备份列出。
4. **界面**：非活动且远端非空时显示“与远端保持一致”和“接入并合并本地会话”。合并动作先显示冲突工作台；确认框明示只改本机、远端不会变化，以及“保留恢复备份”复选项和风险。选择“保持一致”沿用替换确认并允许同一备份选项。
5. **测试与验证**：覆盖无冲突 union、相同 hash 去重、同 UUID 冲突、过期重试拒绝、远端 Head 不被修改、Tracking 在成功应用后更新、未选择保留时成功后无恢复备份。运行 `cargo fmt --all -- --check`、`cargo test --workspace`、`cargo check --workspace`、`cargo clippy --workspace --all-targets -- -D warnings`、`npm run check` 和 `npm run build`。

### 验收标准

- B 的未跟踪会话在“接入并合并”中不会因远端 checkout 而静默丢失。
- 相同 UUID 的不同内容从不自动选边，必须明确选择。
- 该动作不调用远端 commit API，远端 Head 保持不变。
- 成功后 B 可在后续普通 Push 中将合并结果发布。
- 用户未选保留备份时，成功操作不会留下可恢复的 checkout 备份；用户选中时保留并可在备份视图发现。
